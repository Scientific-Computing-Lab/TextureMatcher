# Texton matching: reproduction package

*Private during review; the anonymous mirror is the reviewer-facing copy.*

Reproduces "Texton Matching for Texture Interpolation" in three tiers, each
with one entry command. Higher tiers depend on lower ones; start at Tier 1
regardless of what hardware you have.

| Tier | What it needs | What it gives you |
|---|---|---|
| **1. Score** | CPU, numpy/scipy/pandas, the cached features and per-pair CSVs of the results archive | Every macro in `paper/numbers.tex` / `numbers_v2.tex` that is traceable to a file, recomputed and checked against the paper, in `CHECK.md` |
| **2. Rescore** | CPU or GPU, `install/scoring.sh` | Turns a directory of rendered midpoint images into the same feature caches / CSVs Tier 1 reads, then runs Tier 1 |
| **3. Render** | GPU, `install/cnt.sh` and/or `install/texture_mixer.sh` | Renders the midpoints Tier 2 needs, from scratch, for one paper table at a time |

**Current Tier-1 result** (`CHECK.md`, generated by `score_only.py`):
**245 MATCH, 0 MISMATCH, 257 rows checked** (3 rows have no per-pair file
row and 9 are informational; each is annotated in `CHECK.md`).

Placeholders: this README and the Colab notebooks contain exactly two
values to be filled in before release, `CODE_URL` (where this repository is
hosted) and `IMAGES_URL` (where the rendered-image archive is hosted).
Nothing else is left open.

## Tier 1 — score

```bash
pip install -e .
python score_only.py --data-root /path/to/archive
```

Each check is compared to the paper's macro values, which are shipped in
`evidence/paper_numbers/` (`numbers.tex`, `numbers_v2.tex`), so Tier 1 runs
from this repository plus the archive alone; `--paper-root` compares against
another copy instead. The same folder holds `numbers_tmfid.tex`, three
proposed macros (`\TMkFIDlerp`, `\TMkFIDmean`, `\TMkFIDot`: Texture Mixer FID
for Table 1, 82.4 / 79.6 / 79.1) that `score_only.py` recomputes from the
cached Inception features against the canonical reference; they are reported
in `CHECK.md` as informational rows until the paper defines them.

Runtime: a few minutes on one CPU core. Reads cached `.npy`/`.npz` features
and per-pair CSVs; renders nothing. Writes `CHECK.md` and corrected
KID/FID tables into `evidence/`. The archive's 120-pair folder is looked up
as `pairs_120/` (older local copies used a `pairs_for_*` folder name; both
are accepted).

## Tier 2 — rescore

Bridges Tier 3's rendered images back to Tier 1's input format.

```bash
bash install/scoring.sh                          # or: DEVICE=cuda CUDA_TAG=cu121 bash install/scoring.sh
python rescore.py --images RENDERED_DIR --data-root OUT_DIR \
    --dtd-root DTD_DIR --table all --run-score-only
```

Runtime: dominated by feature extraction, roughly 1-3 ms/image on a GPU,
10-30x slower on CPU. For the full paper protocol (1,000 + 1,000 + 200 +
120 images across every table) budget 10-20 minutes on a GPU.

`--images` must be laid out the way Tier 3's scripts write it (see
`rescore.py`'s module docstring for the exact paths); it is not tied to
any one renderer, so images from your own reimplementation work too, as
long as they land in the same directories.

**Gap you should know about:** this generic rescorer computes KID, FID and
per-image realism correctly (these dominate `CHECK.md`), but the balance
("place") column needs `t=0`/native reconstruction anchors and the
`tab:rules` target-endpoint gap needs a `t=1` render, neither of which
every Tier 3 script produces yet (`cnt_1000.py` and `tm_1000.py` do
produce their reconstruction anchors; `cnt_matched_200.py`'s
`endpoint_gap` is left `NaN`, flagged in its own output, and
`generative_120.py`/`cnt_matched_200.py`'s assembled tables have no
anchors of their own either). `app:ceiling` and `tab:app-primitives` don't
go through this generic rescorer at all -- their Tier-3 scripts
(`ceiling_120.py`, `primitives_120.py`) compute and cache their own
specialized features directly in the layout `score_only.py` expects,
since a Hungarian-matched primitive assignment or an encode-decode-decode
round trip isn't "render a midpoint and score it" the way every other
table is.

## Evaluation protocol

All methods, including the GPT comparator, go through one scoring chain. The
code is `texton_matching/scoring.py` (CPU metrics), `rescore.py` (feature
extraction from images) and `score_only.py` (the paper checks).

**Preprocessing.** Each generated image is converted to RGB and resized to
128×128 with Pillow's `resize` (the scoring resolution of the canonical
notebooks, `notebooks/4_x_jackknife_and_final_tables.ipynb`). For feature
extraction the 128-px image is resized to 256×256, then bilinearly to 299×299
(Inception) or 518×518 (DINOv2), and normalized with the ImageNet mean and
standard deviation. Endpoints of the 1,000-pair benchmark are stored at
128×128 (Texture Mixer's native size) and upsampled to 256×256 before CNT
encoding.

**Observers.**
- Inception-v3, torchvision `IMAGENET1K_V1` weights, classifier removed
  (2,048-d pool features): KID, FID and the "Inc" realism.
- DINOv2 ViT-S/14 through timm, `vit_small_patch14_dinov2.lvd142m`
  (384-d features): "DINO" realism and the balance/placement score. This is
  not the Hugging Face `dinov2-base` model; the GPT harness's own secondary
  analysis (`evidence/gpt_image_1_5_experiment/config.yaml`) uses that model and is
  separate from the paper's scores.
- LPIPS (AlexNet) for the ceiling and alignment studies.

**Reference pool.** A frozen set of 2,819 DTD images (seed 2819, 60 per
category), cached as `ref_inc.npy` and `ref_dino.npy` in the archive and
listed in `ref_list.json`. `app:ceiling` uses its own 5,640-image reference of
native 128-px windows (`joint_basis/ref_inc_win128.npy`).

**Metrics.**
- **KID:** unbiased estimator with the cubic polynomial kernel
  `k(x, y) = (x·y/d + 1)^3`. The reference self-term subtracts the kernel's
  own diagonal (the trace), not the number of reference images. The older
  notebooks used the latter form, which raises every absolute KID by about
  0.000245 and cancels in every difference.
- **FID:** Fréchet distance between Gaussians fitted to generated and
  reference features (`scipy.linalg.sqrtm`).
- **Realism:** the continuous k-NN manifold score of Kynkäänniemi et al.,
  k = 3, 1,000 reference samples per manifold, points with radius above the
  median removed, median over five manifolds (seeds 0 to 4). Values of 1 or
  more lie inside the reference manifold.
- **Balance / placement:** `place = d(M,A) / (d(M,A) + d(M,B))` with DINOv2
  distances to the CNT reconstructions of the endpoints; balance is
  `|place - 0.5|`, and the tables report its median.
- **Paired tests:** ΔKID intervals are paired leave-one-pair-out jackknife
  95% intervals (estimate ± 1.96 jackknife standard errors); realism
  differences use a paired bootstrap of the median; p-values for balance and
  target gap are Wilcoxon signed-rank tests.

**Which KID estimator each table uses** (this matches `CHECK.md`):

| Estimator | Tables |
|---|---|
| Full-reference, trace-corrected (all generated images against the whole reference) | Table 3 `tab:generative` and `tab:app-generative`, Table 2 `tab:eqsample`, the Texture Mixer block of Table 1, `tab:app-primitives`, `app:ceiling`, and every ΔKID |
| 20 repeated subsamples, each of size min(1,000, number of images), averaged; trace-corrected | the CNT block of Table 1 and `tab:rules` |

So the Table 3 KIDs (for example 0.0051 for GPT directed) are full-reference
values, not the 20-subsample estimator.

## GPT-Image-1.5 comparator (Table 3)

The comparator is a proprietary image-editing model used as a black box. The
repository ships the prompts, the call records and the per-pair scores; it
does not call the API.

**What was called.** Model `gpt-image-1.5` (an Azure deployment) through the
image-editing interface (`images.edit`, API version `2025-04-01-preview`),
one call per pair and prompt, run serially. Every call used quality `high`,
input fidelity `high`, output size 1024×1024, PNG, `n = 1`, and two ordered
reference images: A first, B second. The input images are the untouched
endpoint files of the 120-pair set as stored (256×256 RGB PNG, per
`evidence/gpt_image_1_5_experiment/data/pairs_manifest.json`). One
1024×1024 PNG came back per call, and none of the 240 scored calls needed a
retry. Sources, all under `evidence/gpt_image_1_5_experiment/`: `config.yaml`,
`runs/call_ledger.jsonl` and the run manifests in `runs/*/manifest.jsonl`.

**The prompts, verbatim.** The files are in
`evidence/gpt_image_1_5_experiment/prompts/`; their hashes are frozen in
`prompts/manifest.json`.

P1, `P1_PERCEPTUAL_SYMMETRIC_v1`: symmetric natural midpoint, series S2,
reported as "GPT symmetric" in Table 3.

```text
You are given exactly two reference images in order: reference image 1 is texture A and reference image 2 is texture B. Generate one single square image M representing a coherent, plausible perceptual texture midpoint between A and B at t = 0.50.

M must be one internally consistent texture that could plausibly exist on its own. Interpolate texture-level properties such as periodicity, orientation, topology, motif or element shape, spatial scale, density, regularity, material appearance, local contrast, and color distribution. Preserve meaningful evidence of both endpoints and aim for approximately equal perceptual texture distance from A and B. Prefer structural and statistical texture cues over semantic object identity.

Do not make a pixel-space blend, alpha blend, cross-fade, transparent overlay, split image, side-by-side composition, collage, or simple average of colors. Do not merely paste motifs from A and B together. Do not include A, B, labels, text, borders, margins, or a presentation panel. Output only M, edge-to-edge. The definition is symmetric: swapping the order of A and B should not change the intended midpoint.
```

P2, `P2_SOURCE_LAYOUT_v1`: directed midpoint that keeps the layout of A and
moves its appearance halfway to B, series S1, reported as "GPT directed".

```text
You are given exactly two reference images in order: reference image 1 is source texture A and reference image 2 is target-appearance texture B. Generate one single square midpoint texture M at t = 0.50 for a directed source-layout appearance interpolation from A toward B.

Preserve the dominant spatial organization, layout, orientation, and large-scale arrangement of A, while moving the appearance of its local texture elements halfway toward B. Interpolate local motif shape, scale, density, regularity, material, local contrast, and color statistics toward B. The result must be one coherent, plausible texture, not two overlaid patterns. Semantic objects that are incidental to texture should not dominate the interpolation.

Do not make a pixel-space blend, alpha blend, cross-fade, transparent overlay, split image, side-by-side composition, collage, or simple average of colors. Do not include A, B, labels, text, borders, margins, or a presentation panel. Output only M, edge-to-edge. This task is directed: A supplies layout and B supplies the target appearance.
```

A third prompt, P0 (minimal), and a path prompt, P3, exist in the harness.
P0 was used in the pilot, the preview and the prompt-ablation series S3;
neither P0 nor P3 enters any paper table.

**Which outputs are scored.** 120 pairs × 2 prompts = 240 outputs, one
`{k}_mid.png` per pair and prompt (`images/S1/{k}_mid.png` for P2,
`images/S2/{k}_mid.png` for P1), joined on the 120 keys of
`pairs_120/pairs.csv`. In the hosted archive they are
`tm_scale1000/gpt/{k}.png` (directed) and `tm_scale1000/gpt_p1/{k}.png`
(symmetric); all 240 files are byte-identical to the hashes recorded in the
run manifests (`evidence/gpt_call_summary.csv`, column `output_sha256`).
The outputs enter the scoring chain above unchanged, through the same 128-px
transform as every other method.

**Latency and cost.** The ledger (`evidence/gpt_image_1_5_experiment/runs/call_ledger.jsonl`) records the
dispatch time of every paid call; per-call latency is recorded in the run
manifests. Over exactly the 240 scored calls (`experiments/gpt_call_stats.py`
recomputes this and writes `evidence/gpt_call_summary.csv`):

| Calls | n | Median latency | Mean latency |
|---|---|---|---|
| All scored calls (S1 + S2) | 240 | 38.38 s | 38.72 s |
| Directed (P2, S1) | 120 | 38.42 s | 38.62 s |
| Symmetric (P1, S2) | 120 | 38.32 s | 38.82 s |

Six of the 240 outputs (three per series) were produced during the earlier
45-call preview and reused unchanged; their latency is taken from the
preview manifest. For comparison, the preview alone had a median of 35.93 s
(`evidence/gpt_image_1_5_experiment/PILOT_GALLERY.md`). The runtime table in
the paper reports 36 s, which corresponds to the preview measurement rather
than to the 240 scored calls. Cost is not recorded in the ledger. Token usage
per call is in the manifests, and `evidence/gpt_image_1_5_experiment/reports/FULL_RUN_REPORT.md` derives a
list-price estimate from it; no billing statement was retained.

**Scoring.** `experiments/generative_120.py` assembles the 120-pair set and
`score_only.py` (section `tab:generative-120`) recomputes the Table 3 rows
from the cached features (`jackknife/feats_g_gpt.npy` and `feats_g_gptsym.npy`
in the archive). Per-pair realism, DINOv2 distances and placement for both
GPT rows are in `evidence/gpt_pair_scores.csv`. The values in the paper are
the final ones: KID 0.0051 (GPT directed) and 0.0087 (GPT symmetric), against
0.0119 for Texture Mixer and 0.0190 for soft OT, on 120 pairs, with the
full-reference, trace-corrected KID described above. `CHECK.md` shows all
four values matching. The file `matching_ablation/gpt_subset_numbers.json` in
the archive holds an earlier summary (KID 0.0056 and 0.0093 for the two GPT
rows, 0.0116 for Texture Mixer, 0.0185 for soft OT). It predates the
rescoring under the canonical reference and the trace correction and is
**superseded**; it is kept in the archive only for provenance and no table
uses it.

**What is not reproducible.** The API outputs are stochastic and the model is
proprietary, so generation cannot be repeated. The repository ships the
prompts, the call ledger (with the account-specific endpoint removed) and the
run manifests; the 240 outputs are hosted at `IMAGES_URL`. The scores are
therefore reproducible from the outputs; the generation is not.

**Figure.** The GPT strip used in the paper (`fig:gptstrip`) shows the first
three pairs by pair id, with columns A | soft OT | GPT directed | GPT
symmetric | Texture Mixer | B. `fig:app-gpt` is the same layout for the first
eight pairs. The panel-assembly code was not preserved (`COVERAGE.md`).

## Colab

Both notebooks use the paper's first five demo pairs (`pairs_120/pairs.csv`,
k = 0006, 0009, 0017, 0022, 0053); every file they check against was computed
for exactly these five. Both build the pairs' 128-px endpoints with the same
function, `texton_matching.data.prepare_demo_endpoints`, which reconstructs
them from a fresh download of the public DTD release (ported from
`notebooks/4_1_protocol_pairs_and_rendering.ipynb`) and falls back to the PNGs
in `evidence/demo_pairs/` if that fails. Both write to
`/content/rendered/A|B/<k>.png`.

Each notebook has exactly one scripted restart, as its own markdown cell
titled "Restart the session now", between the slow one-time install and the
cells that render and score. Every cell after the restart re-adds
`/content/package` to `sys.path` and uses absolute paths, so "Runtime -> Run
cell and below" from the first post-restart cell works in a fresh kernel.
Both notebooks need a GPU runtime and have a `CODE_URL` variable near the
top: set it to where this repository is hosted, or upload `package.zip`
through Colab's file sidebar (it lands at `/package.zip`; both notebooks check
that and `/content/package.zip`).

`colab/reproduce.ipynb` installs CNT (see "Install scripts"), renders the five
pairs with every CNT rule, scores them against a small improvised reference,
and checks the field-linear placement against
`evidence/field_linear_place_1000.csv`, printing PASS or FAIL. Verified on a
Colab T4 with Python 3.13 and detectron2 0.6 built from source (the install
cell takes 5 to 10 minutes, mostly the detectron2 build); the check passes at
a tolerance of 0.01. That tolerance bounds the distance between the freshly
computed and the archived placement of each pair; it depends on the installed
DINOv2/timm version, so a future release could widen the gap without any
change to CNT. If the check ever fails, compare library versions before
suspecting a regression.

`colab/reproduce_tm.ipynb` installs Texture Mixer, renders the same five pairs
with native lerp, target-mean and soft-OT coupling, restarts, and compares the
freshly rendered native-lerp midpoints with the archive's own PNGs in
`evidence/tm_lerp_demo/`. It prints PASS when the maximum absolute pixel
difference is at most 8 and the mean at most 1 grey level, per pair. On a
Colab T4 the maximum difference was 1 grey level and the check passes.
Texture Mixer rendering is deterministic up to GPU nondeterminism, while
feature-based scores depend on the observer version, which is why this check
is pixel-based. A DINOv2 placement table is printed below it for information
only (no assertion); its differences from `evidence/tm_lerp_place_1000.csv`
reflect DINOv2/timm version drift, not a difference in the rendered pixels.

## Install scripts (`install/`)

- `scoring.sh` -- torch, torchvision (Inception-v3 weights, auto-downloaded),
  DINOv2 (via timm's `vit_small_patch14_dinov2.lvd142m` -- see the script's
  header for why this, not `torch.hub`, matches what the notebooks ran),
  LPIPS, einops.
- `cnt.sh` -- a bash port of the exact cell that succeeded on a fresh Colab
  T4, Python 3.13, after several stricter variants failed (that same logic
  is also inlined directly in `colab/reproduce.ipynb`'s install cell, kept
  byte-identical to what was actually tested). Clones CNT at the pinned
  commit `07269302610c92ce38e2dbbe31c492fd09e1c73e`; downloads the
  checkpoint **before** any further pip work, so a Drive rate-limit fails
  fast rather than after a 5-10 minute detectron2 build, and that's the
  *only* hard-failure condition in the script (missing or <1GB checkpoint);
  installs `requirements.in` as a single tolerated call, not line by line
  (line by line "succeeds" at planting CNT's 2024-era pins, which then
  break at *runtime* on Python 3.13 -- old hydra/omegaconf pull in
  `antlr4-python3-runtime` 4.8, raising `ModuleNotFoundError: typing.io`;
  old timm raises `ValueError: mutable default MaxxVitConvCfg`); checks
  `import detectron2` directly and installs it if missing, independent of
  whether CNT's own plain import needed it (it usually doesn't -- see the
  script's header comment); finishes with an explicit
  `pip install -U timm "hydra-core>=1.3" "omegaconf>=2.3"
  "antlr4-python3-runtime==4.9.3"`, which is what actually fixes the
  runtime breakage regardless of what requirements.in just installed; and
  verifies the checkpoint's sha256 prefix against the one recorded in
  the original correspondence notebook's output.
- `texture_mixer.sh` + `environment_tm.yml` -- separate conda env (no
  upper-bounded `tensorflow<X` pin -- see the script's header comment for
  why that's the same class of risk `cnt.sh` had to fix), clones Texture
  Mixer and its `tensorflow_vgg` dependency, downloads the released "earth
  texture" checkpoint before the tensorflow_vgg clone or the tfutil.py
  patch (same fail-fast-on-the-external-download principle as `cnt.sh`),
  patches two Python-3 syntax issues in `tfutil.py`, verifies the
  TF1-on-TF2 shim imports cleanly.
- `vacher.sh` -- clones the Vacher et al. optimization-based baseline at
  HEAD (the notebooks never pinned a commit for it either). Used by
  `experiments/vacher_50.py`.

Every checkpoint URL is a public, unauthenticated Google Drive share the
archive's own notebooks first pulled from (not a link into anyone's
private Drive). Both are verified (2026-09-22) against the authors' own
GitHub READMEs -- CNT's `finetuned-model256.ckpt` ID and Texture Mixer's
"Earth texture" ID match their respective README links exactly; see each
script's header comment for the exact source URLs. CNT's own project page
(`phtu-cs.github.io/cnt-siga24`) is a broken template mixing CNT's title
with an unrelated older project's content and links -- don't use it as a
source; the GitHub README is the one that's correct.
